The module is organized around a layered adapter pattern over Trigger.dev. `trigger-adapter.ts` defines the `TriggerSdkBoundary` interface that isolates `@trigger.dev/sdk` calls (`tasks.trigger`, `wait.createToken`, `runs.cancel`) behind a frozen factory, so workflow logic never imports Trigger types directly. `task.ts` and `goal-task-handler.ts` are the two Trigger task entry points: they parse payloads via Zod schemas, then delegate to production composition. `production-composition.ts` lazily builds the handler from environment variables, resolving per-snapshot `FeatureWorkflowRoles` (specification/planning/implementation/review/verification) and selecting between GitHub and local-git publishers via `composePublicationTarget`. The core state machine lives in `workflow.ts` (feature pipeline) and `goal-workflow.ts` (goal pipeline), both driven by an effect/lease model defined in `types.ts` through the `WorkflowCheckpointStore` interface. `checkpoint-store.ts` provides an in-memory implementation; `postgres-checkpoint-store.ts` persists effects, session reservations, and budget accounting. A separate `outbox.ts` implements a durable outbox pattern for cross-boundary intents (start workflow, approval resume, cancel, cleanup, orphan reconciliation), each effect claimed with a fenced lease before calling the runtime or Trigger SDK. Budget enforcement is centralized in `workflow-budget.ts` and enforced via `admitSession`/`settleSession`. Cross-cutting concerns include `handle-sealer.ts` (AES sealing of runtime handles with AAD binding run/step/role), `runtime-handle-vault.ts` for persisting sealed handles, `verifier.ts`/`goal-verifier.ts` for criterion verification, and `schemas.ts` for all inter-process JSON contracts. Dependency direction flows inward: task handlers → production composition → workflow engines → checkpoint store / runtime / repository; nothing in the lower layers depends on Trigger.
