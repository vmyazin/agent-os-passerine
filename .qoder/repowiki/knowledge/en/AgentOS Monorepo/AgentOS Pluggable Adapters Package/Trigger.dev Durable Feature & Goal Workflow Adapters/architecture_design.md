Layered adapter over `@trigger.dev/sdk` built around a frozen `TriggerSdkBoundary` (`trigger-adapter.ts`) that isolates `tasks.trigger`, `wait.createToken`, and `runs.cancel` behind injectable interfaces so workflow logic never imports Trigger types. Two task entry points — `task-handler.ts` (feature) and `goal-task-handler.ts` (goal) — parse payloads via Zod schemas then delegate to production composition (`production-composition.ts`), which lazily builds handlers from environment variables and resolves per-snapshot `FeatureWorkflowRoles` plus a GitHub or local-git publisher via `composePublicationTarget`. The core state machines live in `workflow.ts` (feature pipeline) and `goal-workflow.ts` (goal pipeline), both driven by an effect/lease model defined by the `WorkflowCheckpointStore` interface in `types.ts`. Two implementations exist: an in-memory store (`checkpoint-store.ts`) for tests and a Postgres-backed store (`postgres-checkpoint-store.ts`) that persists effects, session reservations, and budget accounting. Cross-boundary intents (start workflow, approval resume, cancel, cleanup, orphan reconciliation) are emitted through `outbox.ts`, each effect claimed with a fenced lease before calling the runtime or SDK. Budget enforcement is centralized in `workflow-budget.ts` via `admitSession`/`settleSession`. Cross-cutting concerns include `handle-sealer.ts` (AES sealing of runtime handles with AAD bound to run/step/role), `runtime-handle-vault.ts` for persisted sealed handles, `verifier.ts`/`goal-verifier.ts` for criterion verification, and `schemas.ts` for all inter-process contracts. Dependency direction flows inward: task handlers → production composition → workflow engines → checkpoint store / runtime / repository; lower layers never depend on Trigger.
